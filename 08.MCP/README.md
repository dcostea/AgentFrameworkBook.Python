# Chapter 08 — MCP tools, resources, prompts and agents

Python ports of all four [`dcostea/AgentFrameworkBook`](https://github.com/dcostea/AgentFrameworkBook/tree/main/08.MCP) projects. These are **motor simulations only**: movement prints a message to stderr and waits; no hardware is accessed.

## Dependencies and configuration

Validated with Python 3.13 and these **already installed** packages:

- `agent-framework-core==1.8.1`, `agent-framework-openai==1.8.1`
- `mcp==1.27.2` (**`mcp.server.fastmcp.FastMCP`**, not the separate `fastmcp` package)
- `uvicorn==0.49.0`, `starlette==1.3.1`
- Existing root dependencies: `openai`, `pydantic`, `python-dotenv`.

No chapter code installs packages. Root configuration files and existing helpers are unchanged. All commands below run from the repository root, using its existing virtual environment.

Protocol discovery, direct tool calls and stdio diagnostics need **no API credentials**. The agent uses `shared.chat_clients.create_sdk_client` / `create_completion_client`, and accepts optional `--provider openai` (default) or `--provider azure`:

| Provider | Environment / existing root `.env` configuration |
|---|---|
| OpenAI | `OPENAI_API_KEY`; optional `OPENAI_CHAT_MODEL_ID` (helper default `gpt-5.4-mini`) and `OPENAI_BASE_URL` |
| Azure OpenAI | `AZURE_OPENAI_ENDPOINT`, `AZURE_OPENAI_API_KEY`, `AZURE_OPENAI_DEPLOYMENT_NAME`; optional `AZURE_OPENAI_API_VERSION` for legacy routing; otherwise the helper uses the v1 endpoint |

Credentials are loaded only when the agent is selected. Agent runs invoke the configured model and may incur charges. No live model calls are made by tests.

## Run the stdio pair

```powershell
.\.venv\Scripts\python.exe .\08.MCP\MCPClientWithStdio\main.py
# Or select Azure for the optional agent:
.\.venv\Scripts\python.exe .\08.MCP\MCPClientWithStdio\main.py --provider azure
```

The client automatically launches the absolute sibling `MCPServerWithStdio\main.py` using **the current `sys.executable`**, not a developer-specific path, `dotnet`, `npx` or a downloaded executable. UTF-8 and unbuffered output are set for the subprocess. The process/transport/session are scoped with SDK async context managers and shut down on completion. Server logs and all `MOTORS:` messages go to **stderr**, with no ANSI output generated by our code; stdout is exclusively JSON-RPC. Each entry point resolves imports using `Path(__file__).resolve().parents[2]`.

As in C#, the client lists tools, prompts, resources and resource templates, then runs:

1. `turn_left` with `angle=99`: `turned anticlockwise 99°.`
2. `run_diagnostics_with_progress`: one ordinary request reports `notifications/progress` for motors `1/4` through `4/4`.
3. `run_diagnostics`: explicitly opt into a real background MCP task, poll `tasks/get`, then retrieve `tasks/result`, with a 30-second timeout.

It retrieves both message prompts, `resource://mcp/bio`, and `resource://mcp/greet/Robby`. The demos take roughly **10 seconds**, plus startup. Finally:

```text
Run the AI agent? [y/N]
```

Enter, `n`, or EOF skips the agent **without loading credentials**; only `y` (case-insensitive) runs it. `MCPStdioTool` exposes discovered tools to a real Agent Framework `Agent`, reusing the initialized SDK session. Prompts are fetched directly, not added as extra model-callable tools.

The standalone server command is useful for an MCP client that supplies stdin/stdout:

```powershell
.\.venv\Scripts\python.exe .\08.MCP\MCPServerWithStdio\main.py
```

## Run the HTTP pair

Start the server explicitly in one terminal, then the client in another:

```powershell
.\.venv\Scripts\python.exe .\08.MCP\MCPServerWithHttp\main.py
.\.venv\Scripts\python.exe .\08.MCP\MCPClientWithHttp\main.py --provider openai
```

Both default to **`http://127.0.0.1:3001/mcp`**. Override the shared port with `MCP_PORT` in the environment or `--port` on **both** commands:

```powershell
.\.venv\Scripts\python.exe .\08.MCP\MCPServerWithHttp\main.py --port 3101
.\.venv\Scripts\python.exe .\08.MCP\MCPClientWithHttp\main.py --port 3101 --provider azure
```

Binding is loopback-only. The server is **stateless Streamable HTTP**, matching C# `.WithHttpTransport(o => o.Stateless = true)`; FastMCP's conventional `/mcp` endpoint replaces C#'s root endpoint. The client does not start the HTTP server. It preserves the source HTTP sequence: all four listings, `turn_left(99)`, both message prompts and both resources, then **immediately** runs the model agent (no confirmation question and no progress/polling demos). `MCPStreamableHTTPTool` integrates the same initialized session into `Agent`. Stop the explicitly started server with Ctrl+C. No remote endpoints are contacted for MCP.

## Protocol/source parity

Both servers identify as `Motors Server` version `1.0.0` and expose:

| MCP name | Inputs | Text result |
|---|---|---|
| `backward` | integer `distance` | `moved backward for {distance} meters.` |
| `forward` | integer `distance` | `moved forward for {distance} meters.` |
| `stop` | none | `stopped.` |
| `turn_left` | integer `angle` | `turned anticlockwise {angle}°.` |
| `turn_right` | integer `angle` | `turned clockwise {angle}°.` |
| `run_diagnostics` | none | `Diagnostics complete. All 4 motors passed.` |
| `run_diagnostics_with_progress` | none | same final result, four progress updates |

Movement delay is **100 milliseconds on both source servers**, not seconds. Diagnostics wait two seconds; progress waits two seconds **per motor** on both transports. Movement uses the original titles/read-only/destructive/idempotent/open-world annotations; `backward` retains `_meta.category="motor"`. Diagnostics are read-only, non-destructive, idempotent and closed-world. Results remain unstructured text (no new output object or renamed output fields). Input boundaries retain signed C# `int` values, including zero/negative values; there is no new physical-distance/angle clamp. Non-integers and out-of-range values are rejected.

Resources retain names **`bio`** / **`greet`**, static URI **`resource://mcp/bio`**, and template **`resource://mcp/greet/{name}`**, returning `text/plain` with the requested URI. `bio` says `My name is Robby, the robot.`; `greet` includes the connected client version or `none`. On stateless HTTP, the read request has no remembered initialize parameters, so `Version: none` is expected; stdio keeps the connected client version. URI-escaped names are decoded for the greeting.

Prompts retain **`string_prompt`**, **`message_prompt`**, and **`parametrized_message_prompt`** with required string argument **`action`**. The string prompt preserves the original trailing space after `Complex command: `; message prompts contain one user message and interpolate the action verbatim. The Agent uses the retrieved parameterized prompt, original robot instructions, and discovered MCP tools.

## Tasks limitations — explicit, not silently omitted

The downloaded C# stdio sample uses `ModelContextProtocol.Extensions.Tasks==2.2.0` and states it requires protocol **2026-07-28**. Python **mcp 1.27.2 negotiates at most 2025-11-25**, and offers Tasks only via its **experimental low-level SDK APIs**, not stable FastMCP decorators. Thus this is a working, real Python Tasks demonstration, **not a claim of compatibility with the newer C# extension version**.

A small `MotorsServer(FastMCP)` adapter registers the pinned SDK's `server.experimental.enable_tasks()`, `request_context.experimental.run_task()`, and task execution metadata. The stdio client uses `session.experimental.call_tool_as_task()`, `poll_task()`, and `get_task_result()`. Ordinary calls remain ordinary; only requests with a task field are offloaded. HTTP deliberately **does not advertise/support Tasks**, as in its source program. Progress is independent of polling.

Task state uses the SDK in-memory store: it is session-scoped, lost on restart, and lazily expires (default client TTL 60 seconds). Python uses its SDK poll interval (**500 ms**, versus C#'s configured 250 ms). Cancellation cancels the simulation coroutine; timeout attempts `tasks/cancel`. HTTP progress notifications explicitly include the originating request ID using the public SDK session API; FastMCP 1.27.2's `Context.report_progress()` alone does not route them onto a stateless HTTP POST stream. The pinned SDK emits `ResourceWarning: Unclosed <MemoryObjectReceiveStream>` during SSE response cleanup. A minimal **unmodified FastMCP** stateless ASGI initialize request, using only `httpx.ASGITransport` (no chapter adapter or MCP client/session), reproduces one warning. Tracemalloc identifies its allocation at `mcp/server/streamable_http.py:584`: the per-response `sse_stream_reader` passed to `EventSourceResponse` at lines 628–630. The successful SSE path does not close that reader; only its exception path closes it at line 643. `_clean_up_memory_streams()` at lines 364–376 closes the separate request-stream pair, not this SSE reader. With installed `sse-starlette==3.4.4`, `_stream_response()` at lines 350–376 closes the body iterator only on send timeout, not normal exhaustion. The same SDK-only probe with `json_response=True` has zero warnings, but JSON mode drops streaming progress, so this chapter retains SSE. Client sessions close their input/output streams in `mcp/shared/session.py:353–358`; chapter code also scopes the HTTP client and MCP transport. No private cleanup patch, package edit, or warning suppression is applied. Tests verify that listeners shut down and ports are released. Agent Framework experimental-feature and uvicorn/websockets deprecation warnings may also appear; dependency internals are not patched or upgraded. FastMCP has no public server-version or task registration constructor options, so the adapter accesses its pinned `_mcp_server`; this must be reviewed when upgrading MCP. Client initialization is bounded at ten seconds; the SDK has no matching public FastMCP initialization-timeout setting. No tasks are persisted or distributed, and no motors/maintenance history are tracked beyond diagnostic tasks (the C# tools likewise have no motor state).

References: [Microsoft Agent Framework MCP guide](https://learn.microsoft.com/agent-framework/agents/tools/local-mcp-tools?pivots=programming-language-python), [official Python MCP SDK](https://github.com/modelcontextprotocol/python-sdk/tree/v1.27.2), [C# Tasks documentation](https://csharp.sdk.modelcontextprotocol.io/v2/concepts/tasks/tasks.html).
